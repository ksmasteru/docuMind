# What I learned — 4 October 2026

Three topics, all met while building the checklist forms feature:

1. **axios**: the response is already parsed, no `.json()`.
2. **Java records**: no empty constructor, build the inner records first, then the parent.
3. **React `useEffect`**: when it runs, why `template` is `null` at first, and how the dependency list works.

---

## 1. axios: the body is already parsed

### fetch vs axios

With the browser's `fetch`, you get a raw response and parse the body yourself. With **axios**, which `apiClient` is built on, the parsing is already done.

```
fetch                                        axios (our apiClient)
─────                                        ─────────────────────
const res  = await fetch(url);               const res = await apiClient.get(url);
const body = await res.json();  ← you parse  const body = res.data;  ← already parsed
```

### What axios actually returns

`apiClient.get(...)` returns a **response object**. Your JSON is **inside** it, under `data`:

```
await apiClient.get("/api/v1/forms/options")
   │
   ▼
{
  data:    { FormItem: [ … ], formsCount: 1 },   ← the JSON the backend sent
  status:  200,
  headers: { … },
  config:  { … },
  ...
}
```

### The two bugs I hit

**Bug 1: calling `.json()`.** The axios response has no `.json()` method:

```jsx
const data = await apiClient.get("/api/v1/forms/options");
const res  = await data.json();   // 💥 TypeError: data.json is not a function
```

The error went straight to the `catch` block, which is why the request looked like it failed even though the backend answered fine.

**Bug 2: forgetting to unwrap `data`.** No crash this time, just silence:

```jsx
const data = await apiClient.get("/api/v1/forms/options");
if (data.formsCount > 0)          // data.formsCount is undefined (it's in data.data)
    setOptions(data.FormItem);    // never runs → empty picker, no error
```

`undefined > 0` is `false`, so `setOptions` never ran and the picker stayed empty.

### The fix: destructure `data`

```jsx
const { data } = await apiClient.get("/api/v1/forms/options");
//    ^^^^^^^^  takes the "data" property out of the response
if (data.formsCount > 0)
    setOptions(data.FormItem);
```

`const { data } = response` is the same as `const data = response.data`.

> **Tip:** when something comes back empty, `console.log` the whole response once. You'll see `status`, `headers`, and your JSON nested inside `data`.

## 2. Java records

### What a record is

A record is a class that only carries data. You list its components once, and Java generates the rest:

```java
public record InspectionFormResponse(
    String id,
    String title,
    ChecklistType type,
    int version,
    String instructions,
    List<QuestionItem> questions)
{ }
```

Java generates:

```
✔ private final fields         id, title, type, version, instructions, questions
✔ ONE constructor taking ALL   new InspectionFormResponse(id, title, type, version, instructions, questions)
✔ accessors                    response.id(), response.title(), …   (no "get" prefix)
✔ equals, hashCode, toString
✘ NO empty constructor         new InspectionFormResponse()       → compile error
✘ NO setters                   response.setTitle(…)               → doesn't exist
✘ NO field assignment          response.title = "…"               → fields are final
```

### A record is built once, with everything

A class like an entity is built **step by step**: create it empty, then fill it. A record is built **in one go**: every value must be ready **before** you call the constructor.

```
ENTITY (mutable)                         RECORD (immutable)
────────────────                         ──────────────────
new CheckListTemplate()   ← empty         gather every value first
   │                                         │
   ├─ setTitle(…)                            ▼
   ├─ setVersion(…)                       new InspectionFormResponse(id, title, …, questions)
   └─ setQuestions(…)                        │
                                             ▼
   can change later                       frozen forever
```

What I first wrote, which doesn't compile:

```java
InspectionFormResponse response = new InspectionFormResponse();  // ✘ no empty constructor
response.id = fetchedTemplate.getId();                            // ✘ final field
response.questions = new ArrayList<>();                           // ✘ final field
```

### Inner records first, then the parent

`InspectionFormResponse` contains a list of `QuestionItem` records. The parent's constructor needs that list as an argument, so **the list must exist first**. Build from the inside out:

```
STEP 1: build each inner record          STEP 2: build the parent with the list
──────────────────────────────           ──────────────────────────────────────
CheckListItem (entity)                   
   │  new QuestionItem(id, position,     
   │      labelAr, labelFr,              items = [ QuestionItem, QuestionItem, … ]
   │      critical, answerType)                         │
   ▼                                                    ▼
QuestionItem  ──► added to items         new InspectionFormResponse(
QuestionItem  ──► added to items             id, title, type, version,
QuestionItem  ──► added to items             instructions, items )   ← list goes in here
```

In code:

```java
// STEP 1: the inner records
List<InspectionFormResponse.QuestionItem> items = new ArrayList<>();
for (CheckListItem question : fetchedTemplate.getQuestions())
{
    items.add(new InspectionFormResponse.QuestionItem(
            question.getId(), question.getPosition(),
            question.getLabelAr(), question.getLabelFr(),
            question.isCritical(), question.getAnswerType()));
}

// STEP 2: the parent, in one call, with the finished list
return new InspectionFormResponse(fetchedTemplate.getId(), fetchedTemplate.getTitle(),
        fetchedTemplate.getCheckListType(), fetchedTemplate.getVersion(),
        fetchedTemplate.getInstructions(), items);
```

The ArrayList itself is mutable, so filling it step by step is fine. Only the **record** is frozen, once it's created.

### Two related lessons

**Nested record names.** A nested record's full name includes its parent: `InspectionFormResponse.QuestionItem`. Two different records both had a nested `FormItem` (creation DTO and response), so `FormItem` alone was ambiguous. Renaming one to `QuestionItem` removed the clash.

**Optional with `orElseThrow`.** `findById` returns an `Optional`, a box that may be empty. Calling `.get()` on an empty box crashes **before** any check after it can run. `orElseThrow` does the check and the unwrap together:

```java
CheckListTemplate fetchedTemplate = checkListTemplateRepository.findById(id)
        .orElseThrow(() -> new FormNotFoundException("no form with id " + id));
```

```
Optional[ template ]  ──.orElseThrow──►  template
Optional[ empty ]     ──.orElseThrow──►  FormNotFoundException  → 404
```

The same family has `.map(...)`: transform the value if it's there, skip if it's empty. Not a loop, just "maybe a value":

```
Optional[ template v3 ] ──.map(t -> t.getVersion() + 1)──► Optional[ 4 ] ──.orElse(1)──► 4
Optional[ empty ]       ──.map(…) skipped ───────────────► Optional[ empty ] ──.orElse(1)──► 1
```

## 3. React `useEffect`

### Props arrive as one object

React calls a component with **one object holding all its props**:

```
<InspectionForm id={selected.value} />
        │
        ▼
InspectionForm({ id: "8e8c…" })
```

```jsx
function InspectionForm(id)    { … }   // ✘ id = { id: "8e8c…" } → URL ends in "[object Object]"
function InspectionForm({ id }) { … }  // ✔ id = "8e8c…"
```

The curly braces take the `id` property out of the props object, the same destructuring as `const { data } = response` with axios.

### `useEffect` runs AFTER the render, and the fetch takes time

This is why `template` is `null` on the first render, even though the effect "fetches it":

```
① first render       template = null     ← your JSX runs NOW, with null
② screen painted
③ useEffect runs     fetchForm() starts the request
                     …waiting for the server…
④ response arrives   setTemplate(data)
⑤ second render      template = the form ← only now is the data there
```

Two delays stack up:

1. **The effect runs after the render.** React first draws the component with the initial state, `useState(null)`, then runs effects.
2. **The fetch is asynchronous.** Even after the effect starts, React keeps showing the component with `null` until the server answers.

Reading `template.type` during render ① crashes:

```
TypeError: Cannot read properties of null (reading 'type')
```

The error says `null`, not `undefined`. That was the clue that it crashed **before** the data arrived, not that the field was missing from the body.

### Guarding against `null`

**Option A: `?.` and `??`, for one value.**

```jsx
const questions = template?.questions ?? [];
```

```
template?.questions                       something ?? []
   ├─ template null → undefined, no crash    ├─ null / undefined → []
   └─ template ok   → template.questions     └─ anything else    → something
```

| `template` is | `template?.questions` | `questions` |
|---|---|---|
| `null` (before fetch) | `undefined` | `[]` |
| the loaded form | the list | the list |

**Option B: an early return, for the whole component.**

```jsx
if (!template) return <p>Loading...</p>;
```

Everything below this line only runs once the data is there, so `template.type` and `template.title` are safe.

### Rule: all hooks first, early returns after

React identifies hooks by **the order they're called in**, on every render. An early return placed above a hook would skip that hook on some renders but not others.

```jsx
export default function InspectionForm({ id }) {
  const [template, setTemplate] = useState(null);   // hook 1
  useEffect(() => { … }, [id]);                      // hook 2

  if (!template) return <p>Loading...</p>;           // ✔ after ALL hooks

  return ( … );
}
```

```
✘ WRONG ORDER                               render 1 (null)   render 2 (loaded)
useState                                    ✔ called          ✔ called
if (!template) return …                     returns here      continues
useEffect                                   ✘ skipped         ✔ called
                                            → 1 hook          → 2 hooks   💥 React error
```

### Re-render vs mount

When the parent passes a new `id`, React **does** call `InspectionForm` again. But calling the function again is not the same as starting fresh:

```
                      MOUNT (first time)              RE-RENDER (props changed)
                      ──────────────────              ─────────────────────────
function called?      yes                             yes
useState(null)        creates state: null             returns the EXISTING state
                                                      (still the old template!)
useEffect(fn, deps)   always runs                     runs ONLY if deps changed
```

Two surprises:

1. **State survives re-renders.** The `null` in `useState(null)` is only used the very first time.
2. **An effect doesn't run on every render.** After each render, React compares the dependency list with its previous values, and runs the effect only if something changed.

### The dependency list

**With `[]`**, the effect runs once, at mount:

```
                       deps   previous   now      changed?   effect runs?
mount                  []     —          —        —          yes (always on mount)
id: crane → permit     []     []         []       no         NO → old form stays on screen
```

**With `[id]`**, the effect reruns whenever the id changes:

```
                       deps   previous   now        changed?   effect runs?
mount                  [id]   —          [crane]    —          yes
id: crane → permit     [id]   [crane]    [permit]   yes        YES → fetches the permit
                                                                 → setTemplate → new render
```

> **Rule:** a re-render reruns your function, but effects only rerun when their dependencies change. List **the values the effect uses to build its work**. The form effect uses `id`, so `[id]`. The options effect uses nothing that changes, so `[]`.

**The mistake I made:** I first put `[selected]` on the **options** effect in Forms.jsx instead of `[id]` on the **form** effect in InspectionForm.jsx. That reloaded the options list on every pick, which was useless, and still never reloaded the selected form.

### Alternative: `key` forces a fresh mount

To get a brand-new component, with fresh state and a fresh mount, every time the selection changes, give it a `key` in the parent:

```jsx
<InspectionForm key={selected.value} id={selected.value} />
```

```
key changes  →  React destroys the old component  →  mounts a new one
                                                      ├─ useState(null) again → "Loading..."
                                                      └─ useEffect runs (mount)
```

| | `[id]` in deps | `key` on the component |
|---|---|---|
| What happens on change | same component, effect reruns | old one destroyed, new one mounted |
| Old state | kept until new data arrives | reset to initial values |
| When to use | refetch on change (usual choice) | reset **all** state, e.g. a technician's half-filled answers |

## Cheat sheet

```
axios        const { data } = await apiClient.get(url);     no .json(), body is in .data

records      no empty constructor, no setters, final fields
             build inner records → collect in a list → new Parent(…, list)

Optional     repo.findById(id).orElseThrow(() -> new XNotFoundException(…))

props        function Comp({ id })                          destructure, don't take (id)

useEffect    runs AFTER render; fetch is async → first render sees initial state
             guard:  value?.field ?? fallback   or   if (!data) return <Loading/>
             hooks first, early returns after
             deps = values the effect uses; [] = mount only; [id] = when id changes
             key={…} on the component = full reset (new mount)
```
